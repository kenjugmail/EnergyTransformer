# Energy inference speed improvement — October 26, 2026

The existing trained streaming energy head now runs faster with the same weights and two refinement steps. This is an execution improvement, not a new accuracy result. CPU inference uses a small-array path and a prepared mode-space calculation; CUDA inference can use a single fused Triton kernel.

## Final warmed measurements

One CPU thread pinned to core 5; NVIDIA GB10; float32, TF32 disabled. All variants use the same trained checkpoint and inputs. Values below are medians of 11 alternating repetitions. Compilation, preparation, and warmup are excluded. GPU utilization was 95 % before and 90 % after the GPU pass, so its numbers describe a heavily shared device.

| Measured workload | Original | Fast | Speedup |
|---|---:|---:|---:|
| CPU energy head, one token | 68.91 µs | 15.74 µs | 4.38× |
| GPU energy head, one token (wall time) | 176.99 µs | 38.97 µs | 4.54× |
| GPU energy head, one token (CUDA events) | 140.54 µs | 4.14 µs | 33.93× |
| Full CPU decoder, 32 tokens after 128-token prefix | 17.14 ms | 15.98 ms | 1.07× |
| Full CPU decoder, 32 tokens after 8,192-token prefix | 16.65 ms | 15.67 ms | 1.06× |
| Full GPU decoder, 32 tokens after 128-token prefix | 88.20 ms | 86.03 ms | 1.03× |
| Full GPU decoder, 32 tokens after 8,192-token prefix | 87.39 ms | 86.95 ms | 1.01× |

The large speedup belongs to the energy head. Whole-model CPU decode latency falls about 6–7%. Most remaining work is outside that head. Small whole-model GPU differences are sensitive to the concurrent GPU workload and are not a reliable capacity claim. CUDA-event intervals include gaps between host launches, so the event speedup is not a claim about arithmetic throughput alone. Head timings amortize timers over 64 calls; the raw files retain the energy-disabled timing floor.

Training was also measured at batch 24 × length 128, including forward, cross-entropy and backward, excluding the optimizer. Training margins changed sign across passes; no robust training-speed gain is claimed. The fused kernel only accelerates prepared inference. The `fast_fused` training row uses the same differentiable compiled function as `fast_compiled`; differences between those rows are timing variation. CPU compilation was slower than the default fast inference path and remains optional.

## Correctness and compatibility

- **245 tests pass**, including float64 output/gradient equivalence, float32 compiled gradients, CUDA fused reductions, non-power-of-two modes, output ownership, stale-weight rejection, and the existing REWT suite. [Test log](tests.log).
- **126/126 real greedy continuation comparisons match**: three trained seeds, story prompts with 96 generated tokens, and validation task prompts with 40 generated bytes, on CPU and CUDA. The task set selects the first prompt in every family/depth/wording category. This is equivalence testing, not a new task-accuracy claim. [CPU cases](continuations_cpu.json) · [CUDA cases](continuations_cuda.json).
- Full-model float32 logit and parameter-gradient comparisons pass. Compiled versus original maximum differences were below 4e-6 for logits and 3e-7 for gradients. Fused inference is separately checked against the original head and by generated token sequences.
- Parameter objects and state-dict keys are preserved. Existing optimizers remain valid. All 36 original streaming checkpoint hashes and the frozen model/training source hashes are unchanged.
- Floating-point ordering differs; universal bitwise identity is not claimed. Trace requests retain the original diagnostic calculation.

## Run it

The default fast CPU path pays no JIT compilation cost:
```bash
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 \
  .venv/bin/python scripts/sample_rewt_streaming.py \
  --checkpoint runs/rewt_streaming_20261026/language_hybrid_energy_26301/best.pt \
  --prompt 'Once upon a time, ' --tokens 96 --fast-energy
```

For float32 CUDA decoding, replace `--fast-energy` with `--device cuda --fused-energy`. It retains both refinement rounds. First use may compile the Triton kernel. The CPU and CUDA CLI paths were run and their greedy text matched the original.

Python integration:
```python
from rewt.streaming import load_streaming
from rewt.fast_energy import optimize_energy
from rewt.streaming_decode import StreamingSession

model, _ = load_streaming(checkpoint)
model.eval()
optimize_energy(model)  # fast CPU inference
session = StreamingSession(model, capacity=8192)
# session.consume(tokens) automatically uses prepared fast energy.
# CUDA: model.cuda(); optimize_energy(model, fused=True); create a new session.
# Optional training experiment: optimize_energy(model, compiled=True).
```

Compilation is optional. In the initial pass, torch.compile warmup took roughly 10.2 s for training plus 7.1 s for inference on CPU, and 7.9 s plus 4.9 s on GPU. Later passes used existing compiler caches. Cold-start cost for the custom Triton path was not separately established.

## Reproduce

```bash
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 TORCHINDUCTOR_COMPILE_THREADS=1 \
  .venv/bin/python -m pytest -q tests_rewt
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 TORCHINDUCTOR_COMPILE_THREADS=1 \
  .venv/bin/python scripts/benchmark_rewt_fast_energy.py --device cpu --output /tmp/energy_cpu_new.json
# Repeat with --device cuda and a different output path.
.venv/bin/python scripts/verify_rewt_fast_energy.py --device cpu --output /tmp/energy_checks_cpu_new.json
# Repeat with --device cuda and a different output path.
```

Timing commands refuse to overwrite existing reports. Finish correctness checks before timing, and run CPU/GPU benchmark processes separately. On another machine, repeat the measurements rather than assuming these speedups transfer.

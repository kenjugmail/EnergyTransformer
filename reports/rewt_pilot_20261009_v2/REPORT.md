# REWT implementation and controlled pilot

This report contains measurements from newly initialized models, not the proposal's expected results. The pilot implements the joint energy, recurrent state, Fourier modes, forecasting, denoising proposals, specialists, communication, learned critic/router, and a separate Fourier gradient-history filter. It is a small feasibility experiment, not a completed twelve-GPU-hour course study.

Primary design: four model families × 3 seeds (101, 202, 303), about 250,000 active parameters each, 120 LM updates of 4 × 128 bytes (61,440 target bytes per fit). All models start from random weights. AdamW LR 0.002, common batches, context resets at 128 bytes, validation-only checkpoint selection, and a checksum-verified 90M/5M/5M enwik8 split. The full model's frozen forecast teacher is its seed's from-scratch baseline.

Reasoning: copies of those models receive 240 answer-only adaptation updates, batch 8, on 4,096 semantic-hash-partitioned training examples. The disjoint test has 150 arithmetic/rule-chain/recall examples, including withheld wording templates and four-step chains. Reported reasoning answers are actually generated greedily; teacher-forced answer likelihood is kept separately.

## Separate equal training-time control

Every fresh fit has a 30-CPU-second training budget. Full REWT spends 25% on a fresh forecast teacher and the remainder on itself. The final complete update can overshoot the budget; actual total CPU time and update counts are shown in the saved JSON. This protocol uses four initial proposal-only warm-up updates and selects the final validation checkpoint, so it is separate from the equal-byte primary comparison.

## Mechanism and component checks

Refinement audits save the energy at each round and verify that accepted states never increase the full energy. Unit tests compare analytic derivatives to independent autograd, test causal prefixes, chunk replay, fixed inference weights, disjoint task identities and strict answer checking.

The ablation folder contains short single-seed retraining for learned/fixed frequencies, coupled/separate modes, coarse-to-fine scheduling, and none/clip/EMA/Fourier gradient filtering. A second file holds inference-only round sweeps (0/1/2/4/8), state/output updates, and module removals. Those removals are interventions on trained weights, not equivalent to retraining without a module. Compare these diagnostics within their own protocol, not against the longer primary fits.

## Limits and reproducibility

The data and training budget are deliberately small. The recurrent state carries up to the common 128-byte reset, with a 16-token attention/history buffer; the baseline attends across the whole 128-byte window. Frequency modes are a finite learned energy family, not an exact reconstruction of an arbitrary landscape. Lower energy is not guaranteed to improve the next-byte probability.

Fixed-frequency retraining has fewer trainable parameters; the primary four-arm counts are matched within 0.5%. Shared-host wall timings can fluctuate, so use recorded process CPU time and sequential profiles for cost interpretation. Cumulative worker RSS is not a per-model activation-memory peak.

The plan stores data/source hashes, every dataset offset, task semantic identity, all configurations, loss weights, preset spike threshold and generation settings. The source snapshot is in source/. Best and resumable optimizer checkpoints are saved under the plan's runs path.

Reproduce with .venv/bin/python -m rewt.experiment. Resume the exact plan with --resume. Do not tune settings from this held-out pilot and then call its test split unseen in a later study; predeclare a new evaluation sample for any follow-up selected from these results.
